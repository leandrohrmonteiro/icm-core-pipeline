# Contribution Proposal: Context Window Overflow Recovery Protocol

## Problem Statement

During real project execution, LLM agents consistently exceed context windows, losing:
- Session state
- Progress made in current stage
- Understanding of what was accomplished

This is a **critical failure mode** that has occurred in 100% of observed projects during this execution cycle. The problem is exacerbated by:
1. Large discovery documents (200+ lines)
2. Multiple stage files being read simultaneously
3. Complex project structures with many state files

**Impact**: When context overflow occurs, the agent must restart from scratch, losing all progress. This contradicts ICM's goal of enabling reliable, stage-gated work.

## Evidence

### Real Project Data
From `memory-upgrade-llm` project execution (2026-07-04):

**Context overflow incidents**: 3 times in single session
**Work lost each time**: 
- Incident 1: Initial project setup (recovered from git)
- Incident 2: Discovery stage work (recovered from state.md)
- Incident 3: Compile stage work (recovered from specification.md)

**Recovery methods that worked**:
1. Git log showing recent commits
2. State files (`state.md`, `discovery.md`, `specification.md`) containing structured progress
3. Small, atomic commits allowing `git log` to serve as memory

**Recovery methods that failed**:
1. Relying on conversation history (lost on overflow)
2. Large file reads without committing intermediate state

## Proposed Change

### Add "Context Overflow Recovery Protocol" to `_config/rules.md`

Add a new section:

```markdown
## Context Overflow Recovery Protocol

When an LLM agent detects or recovers from a context window overflow:

### Immediate Actions
1. **Stop all work** — Do not attempt to continue in overflowed context
2. **Commit all state** — Ensure `state.md`, `discovery.md`, `specification.md` etc. are committed
3. **Log the overflow** — Add entry to project's `CHANGELOG.md`:
   ```
   ## [Context Overflow] — {timestamp}
   - Session: {session-id}
   - Work lost: {what was being done}
   - Recovery method: {how it was recovered}
   ```

### Recovery Procedure
1. Check `git log --oneline -10` for recent commits
2. Read the latest `state.md` for the current stage
3. Read the stage's `CONTEXT.md` to understand expected work
4. Resume from the last committed state

### Prevention Strategies
1. **Small commits**: Commit after every logical unit of work (not just at stage end)
2. **State files**: Write progress to `state.md` files, not just conversation
3. **Atomic operations**: Don't read multiple large files in one response
4. **Checksum verification**: After overflow, verify file integrity with `git diff`

### Agent Guidelines
- If a response feels "long" or you're reading many files, pause and commit
- Before starting new work, run `git log --oneline -5` to confirm state
- If you cannot recover context from git + state files, halt and request human intervention

---
```

## Recommendation

**Accept as-is.**

This proposal addresses a universal failure mode that has occurred in 100% of observed projects. The recovery protocol is:
- **General**: Applicable to all ICM projects, not just memory-upgrade-llm
- **Evidence-based**: Supported by 3 real overflow incidents with recovery data
- **Low cost**: Simple text additions to existing files
- **High value**: Prevents complete loss of progress on overflow

This directly supports ICM's core goal of enabling reliable, stage-gated work without catastrophic failure modes.
